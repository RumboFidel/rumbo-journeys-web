1.2 · Cómo se conecta todo (ruta técnica, en cristiano)

  1. Garmin → Garmin Connect: apenas Fidel termina de correr y el reloj tiene señal/BT, la actividad viaja sola al teléfono.
  2. Garmin Connect → Drive: Fidel exporta la actividad (o la deja auto-sincronizar; ver §1.4) y queda en la carpeta de Drive del día.
  3. FidelApp → Drive: fotos, audios y notas se suben con el botón ☁ que ya programaste.
  4. Drive → PC de Fidel: "Drive para escritorio" replica esa carpeta en el disco. Ahora el agente puede "verla" como una carpeta normal.
  5. Agente IA → borradores: cada mañana lee lo nuevo, redacta y guarda un borrador.md con 3 opciones de texto.
  6. Rutina de GitHub → visor: ⭐ una automatización programada recoge los datos de Drive, los convierte al formato del visor y los publica. Este es el paso que conecta la captura con el visor (detalle en §1.3).
  7. Borradores → Web: Fidel elige/edita en la web (Lovable) y publica el mundo correspondiente.
  8. Web/IA → Redes: el texto aprobado se programa en Instagram y Facebook.

1.3 · Cómo viajan los datos de Drive al visor (las rutinas / GitHub) 🔁

Esta es la parte que faltaba en tu pregunta. Los datos no pasan solos de Drive al visor: hace falta un "cartero automático" que a una hora fija vaya a Drive, recoja lo nuevo, lo traduzca al formato del visor y lo publique. A ese cartero lo llamamos rutina o automatización.

¿Qué es GitHub y por qué aparece aquí?

  • GitHub = la bodega del código del visor. Ahí vive la página del visor.
  • GitHub Pages = la vitrina. Publica esa página en internet gratis (una URL pública).
  • GitHub Actions = el cartero. Es una rutina programada (tipo alarma diaria) que corre en la nube de GitHub, sin necesidad de tener un PC encendido.
🚚 Lo que hace la rutina, paso a paso
  1. Se despierta a una hora fija (ej. 8:00 a.m.) — esto se llama cron.
  2. Entra a la carpeta de Google Drive y busca carreras nuevas.
  3. Toma metadata.json + garmin.gpx + fotos y los convierte al formato que el visor sabe leer (ej. un datos.json del sitio).
  4. Guarda ese resultado en GitHub y publica → el visor queda actualizado con la carrera del día.

Tres formas de montar esta rutina (de más simple a más robusta)

OpciónCómo funcionaVentaja / cuándo usarlaCosto
A. El propio agente de IA para empezarEl mismo agente de Claude que redacta (§1.4) también genera el datos.json del visor y lo sube a GitHub.Menos piezas: una sola rutina hace texto + publicación. Ideal mientras aprenden.Gratis + centavos IA
B. GitHub Actions recomendada al crecerRutina programada en la nube de GitHub. Lee Drive (con la API de Google), convierte y publica. No depende de ningún PC encendido.La más confiable y "profesional". Corre sola aunque todos estén dormidos.Gratis (repos públicos)

💡 RecomendaciónArrancar con la Opción A (el agente de IA también publica al visor) porque es una sola rutina y Fidel entiende todo el flujo. Cuando el proyecto crezca o quieran que funcione sin PC encendido, pasar a GitHub Actions (B). Así encaja también tu plan de "empezar en Lovable y migrar a Claude Code": el visor y su rutina de GitHub pueden convivir con ambos.

1.4 · Tu idea del "agente que se alimenta solo cada día" — ¿es viable?

✅ Respuesta corta: SÍ, es muy viable — y es de las mejores ideas del proyecto. Lo que imaginaste (un agente que cada día lee una carpeta de Drive sincronizada en el PC de Fidel y genera los textos) se puede montar hoy, casi todo gratis. Pagarías solo el consumo de la IA, que son centavos por historia.

Hay tres formas de hacerlo, de la más sencilla a la más automática. Te recomiendo empezar por la Opción A y subir de nivel solo si hace falta.

Opción A — Semiautomática con Claude (la más fácil para aprender) recomendada para empezar

  • Fidel (o tú) abre Claude (app de escritorio o web) y arrastra las fotos + el notas.txt + las métricas del día.
  • Un prompt guardado (te lo dejo listo abajo) hace que Claude devuelva 3 versiones del texto: una emotiva, una informativa y una corta para redes.
  • Ventaja: cero configuración técnica, Fidel ve y entiende cada paso. Ideal como primera etapa de aprendizaje.

Opción B — Agente diario automático con Claude Code + tarea programada nivel intermedio

  • En el PC de Fidel se instala Claude Code apuntando a la carpeta que sincroniza "Drive para escritorio".
  • Se crea un agente programado (Claude Code tiene tareas/cron) que cada mañana a las 7:00 revisa si hay carpetas nuevas, lee todo y escribe borrador.md con las 3 versiones.
  • Como el archivo está en la carpeta de Drive, se sube solo y tú/Fidel lo ven desde cualquier lado.
  • Esto es exactamente el "Claude Cowork / agente que se alimenta solo" que describiste. Es real y viable.
🧠 Sobre "Claude Cowork"Lo que buscas se logra con Claude Code (el asistente de escritorio que ya estás usando conmigo) y sus tareas programadas / agentes. Puede leer una carpeta local, mirar fotos, entender las notas y escribir archivos de vuelta — sin que Fidel tenga que hacer nada cada día.

Opción C — 100% en la nube (sin depender del PC encendido) avanzado, más adelante

  • Una automatización (Make.com o Google Apps Script, ambos con capa gratis) detecta archivos nuevos en Drive y llama a la API de Claude.
  • Ventaja: funciona aunque el PC de Fidel esté apagado. Desventaja: más piezas técnicas; lo dejaría para cuando ya dominen A y B.

1.5 · Capturar las métricas del Garmin lo más automático posible

Las métricas que pides (km, VO₂ máx, fatiga, calorías, frecuencia) las mide el reloj y viajan solas a Garmin Connect. El reto es sacarlas de ahí hacia Drive/web. Opciones, de más simple a más automática:

MétodoCómo funcionaAutomatizaciónCosto

💡 Recomendación prácticaEmpezar con Exportar manual (es 1 minuto y Fidel entiende qué pasa) y, en paralelo, activar la sincronización con Strava que es gratis y automática. La API oficial de Garmin déjenla para v2 si de verdad hace falta, porque implica trámite de aprobación.
⚠️ Ojo con "fatiga"Garmin no tiene un dato llamado exactamente "fatiga". Lo más parecido es Body Battery, Training Load o el estado de entrenamiento. Hay que decidir con Fidel cuál de esos mostrar como "fatiga" en la web (queda en Decisiones).

Capítulo 2 · Desarrollar la primera versión funcional del Lovable 🎨

En esta clase pasamos del prototipo de Google Stitch a una primera pantalla funcional en Lovable. La regla de oro de hoy: solo la pantalla de inicio (los 4 mundos), respetando los textos y el diseño que ya existen. Las demás pantallas se desarrollan después, una por una.

2.1 · Qué vamos a lograr en esta sesión

  • Exportar el diseño desde Google Stitch (un .zip + el design.md).
  • Armar el prompt correcto para Lovable.
  • Generar en Lovable la primera pantalla (los 4 mundos) sin que la IA cambie textos ni diseño.
💡 Idea para enseñarle a FidelGoogle Stitch es "el plano/dibujo" de la casa; Lovable es "el constructor". Le pasamos el plano (zip) y el manual de estilo (design.md), y le pedimos que construya una sola habitación primero: la pantalla de inicio.

2.2 · Paso 1 — Exportar el diseño desde Google Stitch

a) Exportar la pantalla como .zip

  1. Abre tu proyecto en Google Stitch y selecciona la pantalla/imagen que vas a exportar (la de inicio con los 4 mundos).
  2. Arriba, haz clic en los tres puntos ⋮.
  3. Selecciona Exportar y elige el formato .zip.
  4. Guarda ese .zip en tu carpeta del proyecto (o en Drive) para tenerlo a mano.
📦 ¿Qué trae ese ZIP?Trae la estructura y los recursos de la pantalla (imágenes, íconos, y el código base que generó Stitch). Es lo que Lovable va a "leer" para reconstruir el diseño.

b) Copiar la paleta de diseño (design.md)

  1. En Stitch, selecciona la paleta de diseño del proyecto.
  2. Ve al archivo design.md (el "manual de estilo": colores, tipografía, espaciados).
  3. Cópialo completo — lo vas a pegar dentro del prompt (paso 2).
🎨 ¿Por qué importa el design.md?Es lo que le da a Lovable el contexto visual: qué colores, qué letra y qué estilo usar. Sin él, Lovable "inventa" un diseño propio y pierdes la identidad que ya definiste en Stitch.

2.3 · Paso 2 — Preparar el prompt para Lovable

c) Ahora armamos el prompt. Debe: (1) avisar que se adjunta el ZIP, (2) dejar el espacio para pegar el design.md, (3) dar el contexto de la app, (4) exigir que respete los textos y el diseño ya definidos, y (5) dejar claro que por ahora solo se genera la primera pantalla y que más adelante se le dará info de cada pantalla por separado.

2.5 · Consejos y errores comunes

  • Si Lovable cambia textos: recuérdaselo con "Respeta exactamente los textos del diseño, no los modifiques". Es el error más frecuente.
  • Ir de a una pantalla. No pidas todo de golpe: la calidad baja y es difícil corregir.
  • Guarda versiones. Cuando la pantalla de inicio quede bien, guárdala/nómbrala antes de seguir con la siguiente.
  • El design.md es tu ancla. Si el diseño se "desvía", vuelve a pegarlo y pídele que se ciña a él.
  • Créditos de Lovable: cada generación consume créditos; por eso conviene un prompt claro desde el inicio para no repetir.

2.6 · Cómo carga Fidel el contenido: Google Forms → Google Sheets → página 📝

Fidel no toca código. Llena un Google Form (como una encuesta con campos fijos = los "módulos predefinidos"). Cada respuesta cae en una Google Sheet (hoja de cálculo). La página lee esa hoja y arma las tarjetas sola. Así actualiza en 2 minutos desde el celular.

→
📊 Google SheetCada respuesta = una fila

Cómo se monta (una sola vez)

  1. Crear 2 formularios: "Nueva Carrera" y "Nueva Historia", con los campos fijos:
    • Carrera: Municipio · Número · Título · Texto corto · Fotos (subir archivo) · Video (subir archivo) · Etiquetas.
    • Historia: Categoría (lista) · Formato (blog/fotopostal/video) · Título · Texto · Fotos · Video.
  2. Cada formulario crea su hoja de respuestas automáticamente (botón "Vincular a Sheets").
  3. Publicar la hoja para que la página la pueda leer (ver abajo el método).
  4. En Lovable, el prompt maestro le dice a la app que lea esa URL.

💡 En cristianoPublicas la hoja con un enlace, se lo pasas a Lovable en el prompt maestro, y la página queda "enchufada" a esa hoja: cada vez que Fidel llena el formulario, aparece una tarjeta nueva sola.

El contador "N/221"

221 = total de municipios del recorrido (fijo). N = municipios ya recorridos, y sube solo. Se puede calcular de dos formas:

  • Desde la hoja de Carreras: N = número de municipios distintos ya cargados. Simple y siempre sincronizado con lo publicado.
  • Desde el visor: N = municipios que el visor marca como visitados. Útil cuando el visor sea la fuente oficial de la ruta.

Además, la carpeta/enlace debe quedar como "cualquiera con el enlace puede ver" para que se muestren en la web.

2.6 · Cosas para tener en cuenta en el camino (errores comunes)

  • Transferir el APK solo por Google Drive. WhatsApp comprime y corrompe el APK.
  • Compilar desde el botón de Android Studio, no desde la terminal (falta gradle-wrapper.jar).
  • Memoria (OOM): si Android Studio se queda sin memoria, el proyecto ya trae -Xmx2048m en gradle.properties.
  • Permisos en Android 15: el teléfono de Fidel es Android 15; probar que pida bien ubicación en segundo plano.
  • La primera compilación es lenta (baja dependencias). Es normal, no es un error.
  • Guardar avances en Drive/Git para no perder trabajo entre sesiones.
  • Consultar docs/historial-errores.md del proyecto: ahí están los errores ya resueltos.

2.7 · Cómo entregar el APK a Fidel

  1. En Android Studio: Build → Generate App Bundles or APKs → Build APK(s).
  2. El APK queda en app\build\outputs\apk\debug\app-debug.apk.
  3. Subirlo a Google Drive → compartir el enlace con Fidel.
  4. En el teléfono: descargar, permitir "instalar de orígenes desconocidos", instalar.
